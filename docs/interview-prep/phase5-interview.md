# Phase 5 Interview Prep: The LLM Judge and Review Workflow

This file exists so you can walk into an interview and explain this phase without re-reading code. Read the plain-English summary first, then use the questions to test yourself. Answers are written the way you'd actually say them out loud.

This one covers Phase 5 (the cross-vendor LLM judge, its calibrated confidence threshold, and the human review payload).

---

## What Phase 5 actually is, in plain terms

Phases 3 and 4 built an agent that prices a quote and hard, code-level guardrails that catch the mistakes the article's scenarios plant on purpose: a discontinued part left in, a required part missing, a discount on the wrong category. Those all get blocked before a draft is ever called `ready`. Phase 5 is for the mistakes code guardrails structurally cannot catch: a price that is mathematically self-consistent but was only *predicted* from a handful of peers, or a discount that matches the contract exactly today but the contract expires in three days. Nothing about those is a rule violation. They're judgment calls, and judgment calls are what an LLM judge is for.

Per ADR-0004, the judge is a different vendor from the agent on purpose (Claude Haiku judging GPT-4o's output), specifically so the judge doesn't share whatever blind spot the agent has. Five pieces:

1. **Evidence, not vibes.** Before the judge ever sees a draft, code assembles, for every line, exactly the price-book/contract/graph facts a human would want if they were checking that line by hand: is this price from the list or predicted, and if predicted, from how many peers and how tight a spread; does the discount match the contract, and how many days until that contract expires; is the SKU live, and is every required part present. The judge scores against that evidence, never against the raw draft.
2. **Three dimensions, one honest number.** `price_provenance`, `contract_discount`, `graph_completion`, each 0 to 1. The overall confidence is the *minimum* of the three, not an average, because one badly-supported fact shouldn't get diluted by two good ones. Whichever dimension is lowest also becomes the one thing named in the review payload.
3. **A fast path that costs nothing.** A draft code guardrails already rejected (`needs_review`) never reaches the judge model at all. There's no reason to pay for a second opinion on a question code guardrails already answered; the judge just reports the guardrail's own reason as the fact to check.
4. **A calibrated threshold, not a copied number.** The source article uses 0.85 as an auto-send cutoff. This project builds a 32-case, hand-labeled golden set instead, and derives the threshold by sweeping every observed confidence score and picking the lowest one whose Cohen's kappa against the golden set's own human labels still clears an acceptable bar (0.6). Lower is better here because it means more gets auto-trusted without losing agreement with a human's judgment.
5. **One flagged fact, not the whole quote.** A verdict below threshold writes exactly one `ReviewItem`: the weakest dimension, its evidence, its one-sentence rationale, and the specific line if the evidence only touches one line.

Proof it works, without a live Anthropic key: the acceptance test loads the real, committed golden set and the real calibration/scoring code, and confirms the calibration pipeline separates all 32 cases exactly as labeled, at threshold 0.85, kappa 1.0. The judge model itself was never called for real this phase; the calibration script (`scripts/calibrate_judge.py`) is a dry run by default and the `--yes` flag that spends real money was never passed. That's an intentional, accepted gap: the moment the project has a key, one real run fills it in without touching any code.

## Questions an interviewer might actually ask

### Why is the judge a different model vendor, specifically, and not just a different prompt?

Because the failure mode this guards against is a model missing something it was never going to catch in the first place, not a model being sloppy about instructions. If the agent and the judge are the same underlying model, whatever blind spot that model has (a class of reasoning error, a bias in how it reads certain phrasing) shows up identically in both places, and the "second opinion" is really just the same opinion asked twice. A genuinely different vendor, trained differently, is far more likely to have an uncorrelated blind spot, so agreement between the two actually means something. The project's own research notes (`docs/research/llm-judge-calibration.md`) call this out directly, and it's the entire reason ADR-0004 exists as its own decision record instead of being a footnote in the tech-stack table.

### Why does the overall confidence take the minimum of the three dimensions instead of averaging them?

Because averaging lets a confident, well-supported price hide a shaky discount. Picture a draft where the price is a clean list-book lookup (score 0.98) but the discount is on a contract expiring tomorrow (score 0.3). An average lands around 0.75, comfortably "fine." But the actual risk in that draft is entirely in the discount, and a human reviewing it would want to know about the expiring contract, not a reassuring blended number. Taking the minimum means the weakest fact sets the ceiling, which matches how a careful human actually reasons about a document with one weak link: you don't average your way past the weak link, you go check it.

### The 60 real scenario emails include planted discontinued-SKU and missing-required-part mistakes. Why doesn't the judge's golden set use those?

Because by the time a draft would reach the judge, those three mistake types are already gone. Phase 4's `graph_integrity` guardrail and Phase 3's `contract_discount` guardrail catch a discontinued swap, a missing required part, and a wrong-category discount deterministically, before the draft is ever marked `ready`. A judge that only ever saw those three types would have nothing left to prove itself on, since a `ready` draft by construction never contains them. The golden set instead has to be built by hand around the class of problem code guardrails genuinely can't catch: a predicted price that's internally consistent but poorly supported, and a discount that's technically valid today but about to lapse. That's a real design constraint, not an oversight, and it's the reason the spec explicitly rejects "derive the golden set mechanically from scenario_type" as an approach.

### Walk me through how the 0.85 threshold actually gets picked. Why not just eyeball a number that feels safe?

The source article's own 0.85 is explicitly called out, in this project's research notes, as "not a magic number, it's whatever your reviewers' data says it should be." The actual method (from the paper "Trust or Escalate") is: take every distinct confidence score the judge produced across the golden set, treat each one as a candidate threshold, and at each candidate compute Cohen's kappa between (judge says trust/escalate at that cutoff) and (the human's own label for that case). Pick the *lowest* candidate whose kappa still clears an acceptable bar, here 0.6. Lower is better, not just acceptable, because a lower threshold auto-trusts more cases without giving up agreement with the human labels; that's more coverage at the same safety level. If nothing clears the bar, the script refuses to write a threshold at all and tells you to fix the rubric instead of shipping a number that failed its own check.

### The golden set has 32 cases, oddly split 7/7/5/5/5 instead of something rounder like 30 in even groups. Why?

Because a rounder split doesn't force the calibration to actually earn its answer. With 15 trust cases and 17 escalate cases, if the escalate-case clusters were sized 5 instead of 7, wrongly trusting one entire 5-case cluster still keeps Cohen's kappa just above the 0.6 bar, so the "pick the lowest passing threshold" rule would happily settle for a threshold that misclassifies real cases, as long as the aggregate agreement number still looks fine. At size 7, misclassifying a whole cluster drops kappa to about 0.57, which fails the bar and forces the sweep past both weak clusters onto the one threshold that separates every case correctly. This was worked out by hand with the actual formula before a single line of code was written for this phase, specifically so the acceptance test would prove something real (perfect separation) rather than something merely acceptable (adequate-but-imperfect agreement). It held up exactly as designed: the real run found threshold 0.85, kappa 1.0, on the first try.

### What's the most interesting bug this phase's review process actually caught?

The calibration script was quietly inflating its own Cohen's kappa, and no task-level review caught it, only the final whole-branch review did, because it's a cross-cutting property no single task's diff makes visible. Three of the golden set's 32 cases are `needs_review` fast-path cases: drafts already rejected by code guardrails, which the judge never actually scores, always assigned a placeholder confidence of 0.0 and an "escalate" label. Both the calibration script and the acceptance test were feeding *all 32* cases, including those three, into the kappa computation. Since a fast-path case always scores 0.0 and always escalates, it agrees with its own label at every single candidate threshold, for free, without the judge ever having done anything to earn that agreement. That inflates the computed kappa across the board. It didn't change the final answer in this specific golden set (threshold 0.85, kappa 1.0 either way, because the real cases separate cleanly regardless), but with real, noisier model scores from an actual paid run, that inflation would systematically push the calibration toward a more permissive, less safe threshold. The fix filters the kappa computation down to only the 29 cases the judge genuinely scores, and checks the three fast-path labels separately as a plain structural assertion instead of folding them into the statistic. It's a good example of why a plan needs a final review pass looking at the whole feature end to end, not just each piece in isolation: nothing about Task 8 in isolation looked wrong, the bug was in what got fed into a shared computation across two files that were each individually correct.

### What happens if the Anthropic API returns something malformed, like a non-dict entry or a boolean where a score should be?

It becomes a `JudgeError`, never a raw exception, and that discipline had a real gap the final review found. The client validates that the response has exactly three dimensions, with the right names, no duplicates, each score a number between 0 and 1 with a non-empty rationale. The two gaps: if an individual dimension entry in the response wasn't a dict at all (some malformed nested structure), the code called `.get()` on it directly and would have raised a raw `AttributeError` instead of the intended `JudgeError`, defeating the whole point of the client boundary. Separately, Python's `bool` is a subtype of `int`, so `isinstance(True, (int, float))` is `True`, and a response with `"score": true` would have silently been accepted as a perfectly valid `1.0`. Both are the kind of thing that's easy to miss because the "happy path" test never exercises them, and both got fixed with one guard each: check `isinstance(entry, dict)` before touching it, and explicitly reject `bool` before the numeric range check. It's a small reminder that "validate the shape of untrusted input" has to mean the *actual* shape, including the sneaky cases a type system's own rules (bool-is-an-int) can hide from you.

### The same test-setup bug (a missing `seed_world` call) showed up in four different tasks. What does that tell you?

That a gap in written-out example test code, in a plan document, replicates itself every time a different task's tests need the same fixture data, because each implementer is working from the plan's text, not from each other's tests. Four separate tasks (evidence assembly, persistence, service wiring, API routes) each needed a `quote_requests` row referencing a customer and contract that the plan's own test code never seeded first, so each one independently hit the same foreign-key violation and fixed it the same, already-established way: add the one missing `seed_world(db_session)` call. No implementer tried to work around it differently, which is itself a good sign (everyone reached for the codebase's existing pattern instead of inventing a new one), but it's also a lesson about writing plans: a test snippet that's slightly wrong in the plan document costs real, repeated debugging time downstream, once per task that copies it, and it's worth spot-checking a plan's example test code against the schema's actual constraints before locking the plan, not just trusting that "it's just example code."

### Was there a bug in the database migration itself?

Not in the migration's SQL, but in a file the migration doesn't live in. `migrations/env.py` is where every other module's models get imported so Alembic's autogenerate machinery knows what tables should exist. The new judge module's migration was hand-written directly (`op.create_table` calls, not autogenerated), so it applied and worked fine on its own. But nobody had registered `app.judge`'s models in `env.py` itself. The consequence wouldn't show up today: it would show up the next time anyone runs `alembic revision --autogenerate` for an unrelated future change, because Alembic would see the `judge_verdicts` and `review_items` tables sitting in the real database but *absent* from the metadata it's diffing against, and would generate a migration that proposes dropping both. That's a nasty kind of bug: invisible until months later, in someone else's unrelated change, with an innocent-looking auto-generated migration that would quietly delete two production tables if someone approved it without reading the diff carefully. It's another final-review-only catch, for the same reason as the kappa bug: no single task's tests would ever exercise "what does a future autogenerate run see," because that's a property of the whole repo's state, not of this branch's diff.

### The plan called for a `db.env` file with real API keys and the local dev setup turned out to be more complicated than expected. What happened?

Two separate surprises, both caught by stopping to ask rather than pushing through. First, the backend's local `.env` file turned out to belong to a completely different, unrelated project (different schema, different environment variables, and a real-looking OpenAI key sitting in it) that happened to be sitting in the same directory on the developer's machine. It was untracked and gitignored, so there was no repo-history risk, but it was still worth flagging before touching it rather than silently working around it or "fixing" someone else's file. Second, Docker Desktop on Windows and the WSL-side `docker` CLI turned out to be two genuinely separate daemons on this particular machine, not the single shared engine WSL2 integration usually provides: containers started from one side were invisible to `docker ps` on the other, even though the developer runs their normal Postgres/Neo4j stack from WSL. Both were resolved the same way: notice something didn't match the expected picture, stop, and ask exactly what was different, instead of assuming the first plausible explanation and plowing ahead.

## Quick-reference facts

- Cross-vendor judge per ADR-0004: OpenAI GPT-4o (agent) scored by Anthropic Claude Haiku (`claude-haiku-4-5-20251001`), via a forced tool call (`submit_scores`), never free-text.
- Three fixed dimensions: `price_provenance`, `contract_discount`, `graph_completion`. Overall confidence is `min()` of the three; the minimum's name is also the flagged dimension (alphabetical tiebreak on an exact tie).
- Fast path: a `needs_review` draft never reaches the LLM or the graph; the verdict is built straight from the guardrail's own reason, at zero cost.
- Golden set: 32 hand-authored, hand-scored synthetic cases (`data/judge_golden_set.json`), 15 trust / 17 escalate, deliberately sized (7-case escalate clusters, not 5) so the calibration sweep is forced toward perfect separation rather than a merely-acceptable one.
- Calibration method (the "Trust or Escalate" paper): sweep every observed confidence score as a candidate threshold, keep the lowest one whose Cohen's kappa against the golden set clears 0.6, refuse to write a threshold if none does.
- Calibration over the 29 real (non-fast-path) golden-set cases: threshold 0.85, kappa 1.0. While the phase was built this came from the golden set's own hand-assigned scores; the live-Haiku run happened afterwards (see the addendum below) and, after a prompt fix, agreed: threshold 0.85, kappa 1.00, false-auto-send 0.000, stored in `data/judge_calibration.json`.
- `scripts/calibrate_judge.py` is dry-run by default and `--yes` spends real money (29 Haiku calls, about 11k tokens). Without a calibration file the running service falls back to a documented placeholder threshold (0.8).
- New tables: `judge_verdicts`, `review_items`. New routes: `POST /v1/judge/{estimate_id}`, `GET /v1/review`.
- 598 automated tests, up from 551 before this phase, all passing. Still zero real OpenAI or Anthropic calls anywhere in the suite.
- Eight implementation tasks (five independent, dispatched in a fan-out cluster; three serial), several needed a fix round; one whole-branch review at the end (on the most capable model available) found two cross-cutting bugs no single task's review could see: kappa inflation from fast-path cases, and a missing `migrations/env.py` model registration that would have made a future autogenerate migration silently drop both new tables.
- Known, deliberately deferred gap: the judge always evaluates contract expiry against a fixed dataset date (`DATASET_AS_OF`), not the specific estimate's own `as_of`, because `estimate_drafts` doesn't persist that value yet. Latent today (the POC always uses the default date), needs a schema change to close properly.

## Addendum: the first real calibration run (2026-09-30)

### You calibrated against hand-made scores. What happened when you finally ran the real judge?

It failed its own release gate, which is the gate doing its job. With live Claude Haiku scoring the 29 real golden cases, 3 would have auto-sent when a human labeled them escalate: a price predicted from only 4 peers with a wide band, and two contracts expiring in 26 and 27 days. Haiku noticed the risk in each (its rationale said "moderate risk of lapsing") but scored them 0.65 to 0.73, which sits in the same range as legitimately trusted cases, so no threshold separated them. False-auto-send was 10.3% against a 5% ceiling, so the script refused to write a threshold.

### How did you fix it without just tuning until the number passed?

Three decisions. First, I looked at what separated the two label groups in the golden set before changing anything: every escalate case had 3 to 4 peers or under 30 days to expiry, every trust case had 31 or more peers or 560 or more days. That wide gap meant a round policy number could not be reverse-engineered from the three misses. Second, I put the policy in the judge prompt as explicit anchors (fewer than 10 peers scores 0.4 or lower, a contract expiring within 30 days scores 0.5 or lower) rather than editing the labels or raising the ceiling, because relabeling or loosening the ceiling weakens the safety standard to make a number pass. Third, I ran calibration twice more to check the fix was stable: both gave threshold 0.85, kappa 1.00, false-auto-send 0.000.

### What is the honest caveat on that result?

The golden set has 32 cases and I tuned the prompt against it, so a pass is real but weak evidence. The same prompt also missed 3 cases on one run and 4 on the next before the fix, so the judge is not deterministic. The remedy is to keep growing the set from reviewer corrections (Phase 6 already stores full-evidence eval cases) and to re-run calibration after any prompt or model change.

### Why did the first live call fail before scoring anything?

The API key was organization-scoped, and Anthropic answered 400 asking for an `anthropic-workspace-id` header. Nothing was scored or charged. The fix was operational, not code: create the key inside a workspace. I chose that over adding a workspace-id setting and header to the client, because it keeps configuration out of code for what is really a key-type mismatch.
