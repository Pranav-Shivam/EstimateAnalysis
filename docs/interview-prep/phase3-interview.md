# Phase 3 Interview Prep: The Agent, Pricing Tools, and Guardrails

This file exists so you can walk into an interview and explain this phase without re-reading code. Read the plain-English summary first, then use the questions to test yourself. Answers are written the way you'd actually say them out loud.

This one covers Phase 3 (the agent loop, pricing tools, guardrails) plus a few things from Phases 1 and 2 that a reasonable interviewer would expect you to still remember.

---

## What Phase 3 actually is, in plain terms

Phase 2 turned a messy email into a structured request. Phase 3 is where the system finally tries to answer it: it produces a priced draft estimate, and it has a hard-coded referee that can say "no, that draft is not acceptable."

Six pieces:

1. **Price data.** Phase 1 only gave every part a list price. To do real pricing, three things had to be added: a discount percentage on each contract, a price history for most parts, and a deliberate set of about 10% of parts (65) with no price at all, as if they were brand new. That data is generated by a seeded script so it is reproducible.
2. **Tools.** Plain functions the AI agent can call: find a customer and their contract, search the price book, check stock, find a discontinued part's replacement and any parts it requires, and estimate a price for a part that has none.
3. **The agent loop (LangGraph).** GPT-4o reads the request, calls tools, and eventually submits a draft. The draft goes to the guardrails. If it fails, the agent gets the specific complaints and tries again, up to 3 retries (4 submissions in total). If it still fails, or if it runs out of its 12 turns, the draft is marked "needs review" instead of being sent out.
4. **Guardrails.** Ordinary code, not AI. Four checks run on every draft: required fields are present, the customer is real and is the customer who actually sent the request, every price matches the price book (or is a labelled prediction), and every discount is one the customer's contract really gives.
5. **Persistence and an endpoint.** Each run is saved, and `POST /v1/estimate` runs it.
6. **An acceptance test.** All 10 planted "wrong-category discount" cases from Phase 1 are fed through the real guardrails, and every one is blocked.

The AI never sets a total. Totals are computed by code from the lines.

Proof it works: 274 automated tests pass, none of which call OpenAI. The agent is driven in tests by a scripted fake that plays back pre-written turns.

## Questions an interviewer might actually ask

### Why are the guardrails ordinary code and not another AI check?

Because the property you want is a guarantee, not a probability. "A discount is only allowed on categories the contract covers" is a rule you can state exactly, so it should be enforced exactly. A model asked to check that would be right most of the time, and the times it is wrong are the ones that cost money. The AI is good at reading a messy email and deciding what to look up. The code is good at saying yes or no to a specific rule. Phase 5 adds an AI judge, but on top of this, for the fuzzy questions, not instead of it.

### The AI proposes the discount and the code decides. Why not just have code calculate the discount?

Two reasons. First, real emails say things like "apply our contract rate to the conduit too." If code silently computed the discount, that pressure would never reach the guardrail and you could not show it holding. Letting the model propose a number means the model can be talked into a wrong one, and the guardrail is the thing that stops it. Second, it makes the test honest: the acceptance test scripts an agent that over-applies a discount and proves the block, rather than proving a function that could never be wrong.

### Tell me about the most serious bug the final review found.

The customer bypass, and it is the best story from this phase. The discount check asked: does this contract belong to the customer on the draft? But the customer on the draft was also written by the AI. So a request from a customer with no contract could have the AI write a draft naming a different customer who has a 10% contract, and every check passed. The review's probe confirmed it ended "ready" with a discount applied. The same held for a customer ID that did not exist at all.

The lesson is general: a check that compares AI output against other AI output is not a guardrail. It has to be anchored to something the AI did not write. Here that is the customer on the stored request. The fix gives the guardrails the request's own customer, rejects a draft whose customer differs or does not exist, and refuses any discount at all when intake could not identify the customer.

### What is "price provenance" and why does it exist?

Every price on a draft must come from somewhere checkable. If the line says "list price," it must equal the price book exactly. If it says "predicted," it must equal what the prediction function returns. A price the model made up matches neither and is blocked. Without this, the model could quote a number that looks reasonable and no rule would notice.

### How does price prediction work, and how good is it?

For a part with no price, it takes the median list price of other parts in the same category, and reports a low-to-high range from the quartiles. It needs at least 3 priced peers or it refuses to guess. The result is always labelled "predicted." It is honest to say it is weak: in the synthetic data, list prices are random per part, so the median is close to noise. The design choice is that a prediction is never mistaken for a looked-up price. Phase 5 is where a low-confidence predicted price gets routed to a human. Also worth saying: a web search found nothing on price prediction for unpriced items, only demand forecasting, so this is a design decision of ours, not a researched best practice, and the research note says so.

### There is a fixed date constant, DATASET_AS_OF. Why?

The synthetic contracts have dates from 2023 to 2027, and emails carry no date. Measured against the real current date, only 9 of 125 contracts were active, and none of the 10 planted wrong-category cases. Every discount would look "expired," and you could never demonstrate the category check. So the agent takes an "as of" date that defaults to 2024-09-01, when 117 of 125 contracts are active. It is a documented synthetic-data convention. A real system would use the time the request arrived.

### What are the retry and step limits, and why both?

The agent gets up to 3 retries after guardrail failures, so at most 4 submissions, and at most 12 turns overall. They guard against different things. The retry cap stops an agent that keeps resubmitting the same bad discount. The turn cap stops an agent that never submits at all, for example one that keeps chatting. Hitting either ends the run as "needs review," never as "ready" and never as an error. LangGraph also has its own step limit that had to be raised to 100, because each agent turn uses several of its internal steps and the default of 25 would trip first.

### What is a NaN bypass, and how did it happen?

Not-a-number is a special floating point value, and every comparison with it is false. The first version checked "is the price off by more than a tolerance" and blocked when true. For NaN that comparison is false, so NaN sailed through as if it were correct. A reviewer probed it and confirmed a NaN price or discount passed every check. The fix does two things: reject any non-finite number outright, and flip the comparisons to fail closed, "block unless the difference is within tolerance," so anything odd is blocked by default. The general rule for safety code is to make the default answer "no."

### Several bugs came from something called autoflush being off. Explain.

In this codebase the database session does not automatically write pending changes before a query. So code that adds a row and then looks it up in the same session finds nothing until it explicitly flushes. It bit twice: recording a part's required parts twice raised a duplicate-key error, and the price loader could not find contracts it had just created (this one only showed up when the real loader script ran, because the tests happened to flush first). Each fix was one flush plus a test that reproduced the failure. It is the same lesson as the Phase 2 insert-ordering bug: understand what your ORM does implicitly.

### What happens if the AI sends a wrong-typed argument to a tool?

A subtle one. If the model called the search tool with a number instead of text, that number would be sent to Postgres against a text column, Postgres would raise an error, and that error aborts the entire database transaction. Every later query in the request then fails, so the run would crash with a 500. Catching the exception in the agent loop would not help, because the transaction is already broken. The fix is to check every argument is a string before touching the database and hand the model a plain error message instead.

### A test suite full of mocks can hide real bugs. Did that happen here?

Twice. First, the OpenAI client wrapper was only ever tested against a fake, so the reviewers checked its assumptions against the real library's type definitions. That caught two cases the fake could not: an empty list of choices, and a tool argument that was valid JSON but not an object. Both are now wrapped so they become a clean 502.

Second, a text-only model turn with no content was stored as an empty value, and OpenAI rejects that on the next request. No fake would ever notice. The fix sends an empty string instead.

### Did any tests turn out to be worthless?

Yes, and finding that was a review win. The test meant to prove that certain parts are never chosen as "no price" parts used a random sample that happened to miss all the protected parts, so it passed even with the protection deleted. A reviewer deleted the protection logic four different ways and the test still passed. The fix makes protection the only thing that could explain a part being excluded, then asserts the exact expected set. The same idea applied to the API key test, below.

### What about the API key from Phase 2?

Phase 2's worst bug was that the real key never reached the OpenAI client. Its test tries to catch that but cannot: the OpenAI library reads the key from the environment by itself, and the test sets that environment variable, so the test passes whether or not the code passes the key. The Phase 3 route has a stronger test that deletes the environment variable and supplies the key only through the settings object. The Phase 2 test is still weak and is worth fixing.

### Where does JSON null versus SQL NULL come in?

Storing "no draft" (the agent never submitted anything) in a JSON column wrote the JSON value `null`, not a real database NULL. Reading it back in Python gives None either way, so every test passed. But a query like "find rows where draft is null" would silently miss them. One column setting fixed it, and the test now checks with raw SQL.

### What did you deliberately leave unfinished?

Documented, not hidden:

- The guardrails do not block a draft that leaves a discontinued part in place or omits a required part. Those are handled by the agent's instructions only. Phase 4's graph is the natural place to enforce them.
- Recording an assumed quantity for a vague request ("4 or 5") is also instructions-only.
- The agent run holds one database transaction across up to 12 model calls. Fine for a proof of concept, wrong for production.
- Running the estimate twice writes two rows. Each run is an attempt.
- The whole thing has never run against real OpenAI over the real emails. That costs money and needs your approval.
- The intake step's customer match is trusted. If intake resolves the wrong customer, the guardrails inherit the mistake.

### How was this built, and what did the process catch?

Twelve small test-first tasks. For each one, a fresh implementer wrote the code and a separate fresh reviewer, with no memory of writing it, checked the diff. Then one more strong reviewer looked at the whole branch. Of the 12 tasks, 6 needed a fix round, and most fixes were real bugs, not style. The biggest, the customer bypass, was found by the final whole-branch review, not by any per-task review, because it lives in how three separate tasks fit together.

## Quick-reference facts

- New tables: `sku_requirements`, `price_history`, `estimate_drafts`. New columns: `contracts.discount_pct`, and `skus.list_price` became nullable. Migrations 0002 and 0003 (0003 adds two indexes).
- Price data: 125 contract discounts (5, 8, 10, 12 or 15 percent), 65 price-book gap parts (10%), 1166 price history rows.
- Guardrails: required fields, customer identity, price provenance, contract discount. Checks run in that order.
- Limits: 4 submissions maximum, 12 agent turns, quantity capped at 100,000 per line, LangGraph step limit 100.
- Default quote date: 2024-09-01.
- 274 automated tests, all passing. No test calls OpenAI.
- `POST /v1/estimate` takes a quote request id and an optional as-of date, returns the draft, its totals, any violations, and a status of `ready` or `needs_review`.
