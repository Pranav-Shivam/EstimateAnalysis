# Phase 4 Interview Prep: The Knowledge Graph

This file exists so you can walk into an interview and explain this phase without re-reading code. Read the plain-English summary first, then use the questions to test yourself. Answers are written the way you'd actually say them out loud.

This one covers Phase 4 (the Neo4j knowledge graph, graph query modes, and the hybrid retrieval router) plus the Phase 3 gap it closes.

---

## What Phase 4 actually is, in plain terms

Phase 3 built an agent that prices a quote and a set of guardrails that check its work. But two of the three planted mistake types (a discontinued part left in the quote, a required part left off) were only ever caught by the agent's own instructions, not by a hard check. An instruction is a suggestion the model can ignore under email pressure; a guardrail is a rule that always runs. Phase 4 closes that gap by building an actual graph of how things relate to each other, in Neo4j, and using it two ways: the agent gets tools that walk the graph to find the right answer, and a new guardrail walks the same graph to check the agent's draft, independently of whatever the agent believed.

Six pieces:

1. **A real graph, not a diagram.** Neo4j holds ten kinds of nodes (customers, contacts, contracts, pricing categories, product families, SKUs, sites, projects, quote requests, quotes) and fifteen kinds of relationships between them, matching the shape described in the source article. The graph is entirely rebuilt from Postgres on demand; nothing lives only in the graph. If Neo4j were wiped tonight, one API call rebuilds it exactly, because Postgres is still the source of truth.
2. **A namespace on every node.** The dev graph and every single test each get their own slice of the same Neo4j instance, tagged with a namespace string. A test never sees another test's data, and nothing but one documented final step ever touches the real "main" graph.
3. **Two new tools for the agent.** `get_related_parts` now walks the actual replacement chain in the graph (a part can be replaced by a part that's also discontinued, replaced by a live one) instead of checking one field. `check_contract_coverage` asks the graph whether a customer's contract actually covers a part's category before a discount is proposed, instead of the agent guessing from the contract terms it read in a tool result.
4. **The guardrail that was missing.** `graph_integrity` reads the same graph, independently, and blocks a draft that still has a discontinued part in it, or is missing a part something else on the draft requires. Critically, it doesn't trust the draft to tell it what was asked for — it anchors on the SKU IDs intake resolved by code before the agent ever saw the email, the same way Phase 3's fix for the customer-discount bug anchored on the request's real customer instead of the draft's own claim.
5. **Community detection and two ways to ask questions.** Neo4j's graph algorithms library groups SKUs into clusters (Leiden), and a "local" query mode answers narrow questions (what does this part need) while a "global" mode answers broad ones (what do these clusters of parts look like), the second optionally summarized by a cheap LLM call, cached so you never pay for the same summary twice.
6. **A router that picks the right tool for a question**, without any AI in the loop: a handful of regex rules decide whether a question should go to plain SQL, a graph walk, or a SKU-similarity vector search, in that specific order, because a similarity question mentioning an ID still means "find me things like this," not "look up this ID."

Proof it works: 551 automated tests pass, still zero of which call OpenAI for real. The headline proof is a single test file that takes the actual 30 planted mistake cases from the real dataset (not the small test-fixture world) and runs them through a scripted agent that behaves the way the system prompt asks: it calls the graph tools, gets corrected the first time a guardrail blocks it, and the second submission is `ready`. A second version of the same test never lets the agent learn, and proves none of the 30 cases ever slips through as `ready` anyway.

## Questions an interviewer might actually ask

### Why Neo4j instead of just more SQL tables? Postgres already has foreign keys.

Foreign keys tell you a row points at another row. They don't answer "what's downstream of this, however many hops away, and what did I pass through to get there." "Is A replaced by something that's also replaced by something else" is a fixed-depth chain of SQL joins with no idea how deep to go up front. In Neo4j the same question is one line of Cypher with an open-ended hop count. The relationships this phase needs — a replacement chain, a required-parts graph, a customer's whole contract-and-coverage picture — are genuinely graph-shaped questions, and Postgres was going to end up simulating a graph with recursive CTEs anyway. ADR-0002 made this call up front; Phase 4 is where it actually gets exercised.

### If Neo4j goes down, does pricing stop working?

No, and that was a deliberate design point, not an accident. Postgres stays authoritative. The graph is described everywhere in the code and docs as a "rebuildable projection" — a fancy way of saying it's a cache with relationships. If Neo4j is unreachable, the run doesn't crash: the agent's very first move is a freshness check, and an unreachable or stale graph makes the run end `needs_review` before a single dollar is spent on a model call. The system fails safe, never fails open. What genuinely breaks is the *judgment quality* — you lose the graph-backed catch for a discontinued part or a missing required part — but the customer identity and contract-discount guardrails from Phase 3 are pure SQL and keep running regardless.

### Why does every graph node carry a namespace string? Isn't that just Neo4j's built-in database feature reinvented badly?

Neo4j Community Edition, which is what this project runs (a deliberate ADR-0002 trade-off — free and locally runnable, versus Enterprise's proper multi-database support), only gives you one real database per instance. So instead of one Neo4j server per test, every test gets its own logical slice of the *same* database, tagged by a namespace property on every node and checked on every query. It's not as clean as real multi-tenancy, but it's the actual trade-off Community Edition forces, and it's the same discipline the dev Postgres already uses (tests roll back a transaction instead of getting their own database).

### What's the worst bug this phase's process actually found?

A race condition between a graph rebuild and an in-flight guardrail check, and it's the best story from this phase because no single piece of code was wrong — three separate, individually-correct design choices combined into a real bypass. Rebuilding the graph deletes everything in a namespace first, then reloads it piece by piece. The guardrail checks "is the graph current" once, then makes several separate reads while walking a part's chain. If a rebuild started *after* that one freshness check but *during* those reads, the graph would momentarily look empty — no discontinued flag, no required-parts edge — and the guardrail read that as "nothing to worry about" instead of "the ground moved under me." A final whole-branch review, done last with the most capable model available and deliberately told to hunt for exactly this shape of bug, reproduced it end to end: paused a real rebuild mid-flight with a real guardrail check running against it, and watched a draft with a discontinued part reach `ready`.

The fix: a second freshness check runs right after the graph reads finish, not just before they start, and a Postgres advisory lock stops two rebuilds of the same graph from overlapping at all. The lesson generalizes past this one bug: a single point-in-time check on a bug shape ("is the data current") only proves the data was current at that instant, not for the whole operation that follows it.

### The `match_site` function had a bug in the *plan itself*, not the code. What happened?

Before any code was written, the design called for matching a free-text hint like "the job at 12 Elm Street" against a customer's list of sites, by checking whether the hint mentions a site's zip code or its street. The plan's own written test case said two sites sharing a street name but different zips should resolve unambiguously when the hint includes the zip. But the plan's own reference logic checked "zip matches OR street matches" — and since the street matches *both* sites, that logic sees two matches and gives up, contradicting its own test. The implementer caught this before writing a single line of production code, because TDD means the test comes first: trying to make the test pass against the described logic simply didn't work. The actual fix tries the zip match first, and only falls back to the street match if no zip is mentioned at all. It's a reminder that a design document is a hypothesis, and the first thing that should happen to a hypothesis is someone trying to disprove it.

### How did the guardrail know which SKUs the customer actually asked for, if the agent writes the draft?

This is the direct sequel to Phase 3's worst bug (a guardrail that checked the draft's own customer field against itself, so a bad actor's draft could just claim to be a covered customer). The fix there was to anchor on the quote request's real, code-resolved customer ID, never the draft's own claim. Phase 4 applies the identical principle to parts: when intake reads an email, its fuzzy matching resolves "Chrome Sprayer" to a real SKU ID by code, before any LLM or agent gets involved. That resolved ID list becomes `request_sku_ids`, stored on the tool context the guardrail reads. The guardrail then asks the graph: does the draft actually include the live (non-discontinued) version of every one of those IDs? An agent that quietly drops a line, or swaps in the wrong replacement, gets caught, because the check never trusts the draft to describe what was requested — it always goes back to what was actually asked for, from a source the model never touched.

### What happens with a required part that's five levels deep, or a discontinued part that has no live replacement at all?

Two different, deliberate outcomes. A deep required-parts chain (part A needs B needs C needs D needs E) gets caught one layer at a time: each guardrail failure tells the agent about the *next* missing layer, and it has a limited number of retries (four submissions total) to work all the way down. A chain that's too deep to resolve within that budget correctly ends up `needs_review`, not stuck in an infinite loop and not silently approved — this exact boundary got its own dedicated test during the final review, specifically because "the retry budget runs out safely" is easy to assume and easy to leave unverified. A part that's discontinued with *no* live replacement anywhere in its chain (or one that only cycles back to itself, which the chain-walker caps at ten hops to guarantee it terminates) is treated completely differently: there's nothing a retry can fix, so the guardrail flags it as "unreplaceable" and the run goes straight to `needs_review` without spending any of the retry budget on a problem retrying can't solve.

### Two separate paid-API features (community summaries and SKU embeddings) had almost the identical bug. What was it, and why twice?

Both features process work in batches and call back to the caller after each batch, with a stated promise: "if something fails partway through, whatever was already saved stays saved." Neither feature had a test that actually proved the callback fired *after* the save, not before — a test that just counted how many times the callback ran couldn't tell the difference between the two orderings. It happened twice because the second feature's author, working from a similar-shaped task, copied the same test pattern without independently re-deriving whether it actually locked in the guarantee. The fix, in both cases, was to make the callback itself read the just-saved row back through the same database session and assert it's really there — proving the order without needing a real transaction commit, which the test fixtures in this repo can't safely do (see below).

### Why not just test the "save survives a crash" promise with a real database commit?

Because every test in this backend runs inside one already-open database transaction that gets rolled back at the very end, specifically so tests never leave real data behind in the shared development database. If a test called a real `commit()`, it would commit *through* that outer transaction for real, either breaking every other test's isolation or leaving permanent junk rows in the dev database. So instead of proving durability across an actual crash boundary, the fix proves the weaker but still meaningful property that matters here: within the same request, the save genuinely finishes before the "safe to proceed" signal fires, using the one session already available. It's a case where the textbook-correct test isn't available, and the honest answer is a slightly weaker test with a documented reason, not skipping the test.

### The Leiden community-detection algorithm groups SKUs into clusters. What do those clusters actually mean here?

Less than the name suggests, and that's worth saying plainly in an interview rather than overselling it. Leiden finds densely-connected groups in a graph; in a real recommendation system that graph would be built from purchase history, so a cluster would mean "products people tend to buy together." This dataset has no purchase history at all — the clusters are built purely from product-family membership, required-parts links, and replacement chains, so what Leiden actually finds is closer to "structurally similar products" than "customers who buy X also buy Y." It's a real, working implementation of the algorithm and it does produce sensible-looking groups (the real catalog splits into around 65 communities), but it's honest to say the *data* underneath it doesn't yet support the marketing claim a purchase-history-based system would make.

### What's the router, and why is it plain regular expressions instead of another LLM call?

A question coming into the system's knowledge endpoint could be answered by a straight database lookup ("what's the price of SKU-0001"), a graph walk ("what does SKU-0001 require"), a cluster summary ("which product groups are most exposed"), or a similarity search ("something like a 3-ton condenser"). Routing that decision through an LLM would mean a paid API call, plus non-determinism, just to decide *where to look* before you've even answered anything. Instead, the router is a small, ordered list of regex checks: portfolio-sounding phrasing wins first, then similarity phrasing, then an ID paired with relationship language, then a bare ID, and a plain name search is the fallback. It's free, instant, and — because it's a fixed set of rules — fully covered by a table-driven test that pins down the exact precedence, including the deliberately tricky case where a question mentions both an ID and similarity language ("similar to SKU-0001") and similarity has to win.

### How was this phase actually built, and what did the review process catch that a single reviewer wouldn't have?

Thirteen small, test-first tasks, each with a fresh implementer and a fresh reviewer who actively tried to break the code with real mutation testing — not just reading it, but deliberately breaking a line and confirming a test caught the breakage. Ten of the thirteen tasks needed at least one fix round, and the pattern is telling: almost every one of those catches was a missing *test*, not a wrong line of production code — the namespace-isolation guarantee, the save-before-callback ordering, the retry-exhaustion boundary. The one exception was the rebuild-race bug, which is also the one bug that spans three different tasks' code at once (how rebuilds are ordered, how the freshness check is timed, and that the rebuild endpoint has no access control) — and that's exactly the kind of bug only the final, whole-branch review, done separately from every individual task's review, was positioned to see.

## Quick-reference facts

- Schema: 10 node types (Customer, Person, Contract, PricingCategory, ProductFamily, SKU, Project, Site, QuoteRequest, Quote), 15 edge types, matching the source article's design.
- Neo4j 2026.09 Community Edition with the GDS plugin, in Docker, on host ports 17474 and 17687 (never the defaults, to avoid the port collision hit in an earlier phase).
- The graph is a namespaced projection: `main` for the real dev graph, `test-<random>` for every test, dropped on teardown. Rebuildable from Postgres at any time via one API call.
- New guardrail: `graph_integrity`, anchored on intake-resolved SKU IDs, never on the draft's own claims. Fails closed on an unreachable or stale graph, checked both before the agent loop starts and again on every guardrail pass.
- New agent tools: `get_related_parts` (now graph-backed, walks the full replacement chain), `check_contract_coverage`, `ask_knowledge` (routes to graph or vector search for open-ended questions).
- Leiden community detection via Neo4j's GDS library; on the real catalog, about 65 communities, largest one 42 members.
- Cost-gated jobs, both dry-run by default and requiring an explicit `--yes` flag to spend real money: SKU embeddings (about 650 SKUs, roughly 10,000 tokens) and community summaries (about 57 eligible communities, roughly 11,000 tokens). Neither has ever been run for real in this project; both were only ever exercised against fakes in tests.
- 551 automated tests, up from 274 before this phase, all passing. Still zero real OpenAI calls anywhere in the suite.
- Thirteen implementation tasks, ten needed at least one fix round; one whole-branch review at the end (on the most capable model available) found the one bug spanning multiple tasks: a rebuild-versus-guardrail race, fixed with a second freshness check plus a Postgres advisory lock serializing rebuilds.
- Acceptance proof: all 30 real planted mistake cases (10 discontinued swaps, 10 missing required parts, 10 wrong-category discounts) are blocked then corrected by a scripted agent that actually calls the graph tools; a second test proves none of the 30 ever reaches `ready` if the agent never learns from the guardrail's feedback.
